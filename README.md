# COMP20290 Group 6 Project #

This repository contains Group 6's reproduction of the experiments conducted 
by Carter et al. in their paper "Energy and Time Complexity for Sorting 
Algorithms in Java". This repository aims to measure the performance and 
energy usage of 4 different sorting algorithms for their best, worst and 
random case scenarios.

Group members include **Anton Sohn**, **Quinten Verkammen**,
**Edvinas Dabsevicius** and **Mingaile Michejeva**.


## Sorting Algorithms ##

The 4 sorting algorithms compared by this repository are:

- **BubbleSort**
- **CountSort**
- **MergeSort**
- **QuickSort**

Implementations for each of these can be found within the `/sorters` folder.
These implementations follow the pseudocode algorithms detailed in the paper.

## Performance Measurement ##

The performance of these algorithms can be measured and recorded when running
the `app/Main.java` file. For this, different input sizes and shapes of data 
patterns were used. These can be found under the `/resources` folder. Most 
tests were conducted with input arrays with 25k, 50k, 75k, 100k, 200k, 
[...], 1M elements. More on the input space later.

When `Main.java` is run, results are printed to different results files, 
according to the algorithm being tested. The results detail the time spent
to complete the test, as well as the energy used during these tests. Note that,
depending on the hardware used, it can take a significant amount of time to 
produce all results. Updates of what the program is working on are printed to
the standard output. 

***Important (1):*** Given that very large array sizes are used, this can require
very large overhead from certain algorithms - notably QuickSort & MergeSort. As 
such, the sheer memory required can cause StackOverflow errors during runtime.
Using IntelliJ, we were able to remedy this by increasing allocated memory as 
follows:
- Open the dropdown (typically where it says "Current File") next to the
button used to run files
- Press **Edit Configurations**
- Press **Modify Options**
- Select **Add VM options** from the menu that pops up
- A "VM Options" text box should appear. Here, type the following argument:
`-Xss50m`. This increases the execution stack to 50 MB (up from the 
default 1 MB)
- **Apply** the changes, and run the program through `Main.java`

***Important (2):*** Energy readings are **only** visible when running 
`Main.java` on a **native Linux machine** with an **Intel processor**. This is 
because energy is measured using RAPL, an Intel-exclusive hardware feature which
can only be accessed when running through Linux. Tests performed on Windows 
machines will not output energy used. Using a shell such as Windows Subsystem 
for Linux (WSL) will also not remedy this. It is possible to check whether one's
running environment is able to collect energy readings by running 
`ReadEnergyTest.java`.

## Input Space ##

The inputs used for the testing of the algorithms are generated in this 
repository as well. This takes place in the `app/CSVGenerator.java` file. 
Here, a series of CSV files representing input arrays are generated, mirroring
the paper's input arrays. These CSV files represent the following types of 
data:

- Sorted
- Reverse Sorted
- Alternating elements
- Evenly Partitioned 
- Randomly Sorted

As mentioned before, each of these types of CSV files is generated for an array
size of 25k, 50k, 75k, 100k, 200k, [...], 1M elements to allow for the tracking
of performance across input sizes. Note that for QuickSort, CSVs containing 
reverse sorted data were created for the sizes of 25k to 200k, in steps of 25k. 
This mirrors the original paper as it allows for better analysis of the 
algorithm's behaviour across input sizes. 

While `/resources` is already populated all input files as generated by 
`CSVGenerator.java`, it is always possible to re-generate this data simply by
running said file. Doing so for subsequent benchmarks of the algorithms would
eliminate random variance, given that some of the tests (partially) rely on 
randomly generated arrays.
